## Provenance

The supervisor of Epic 4 found, while reviewing PR #37, that **nothing in the
repository covers publishing**. `grep -rn "npm publish" docs/` matches no
story in any epic; `architecture.md:329` disposes of the whole subject in one
clause — *"npm publishing is manual by the maintainer (AD-11 fixes the
artifact, not a release cadence)"* — which fixes the artefact and deliberately
leaves the act unscheduled.

The evidence that this is a gap and not a decision already taken:

- `packages/cli/package.json` on `epic/4-build-bundle` after PR #37 carries
  `"private": true`, `"name": "@gitnebula/cli"` and `"version": "0.0.0"`. The
  first makes `npm publish` refuse outright; the second contradicts AD-11
  (*"Only `gitnebula` (cli) is published"*), and PR #37 flagged the rename as
  a publish-time act left to the maintainer; the third is not a release.
- `README.md` (PR #36) leads with `npx gitnebula`, which resolves to nothing
  today, and carries a pre-release fallback line pointing readers at a clone.
  FR-1 makes `npx gitnebula` the product's front door.
- The name `gitnebula` was unregistered on the npm registry when this spec was
  written (registry returned 404 on 2026-08-13).

It is a new story rather than a correction to a live one: no story in the
Epic 4 cohort (4.1, 4.3, 4.4) has publishing in scope, and 4.2's ACs are about
GitHub Actions and Pages, not the npm registry.

**Amended 2026-08-13, after the spec first landed (PR #38).** AC-6 — the
dev-checkout asset gap — was added on the maintainer's explicit instruction,
who also waived the supervisor's standing rule against editing an existing
spec for this one change. The finding is story 4.4's, from PR #39; it had no
owner, and this story already opens the two files it touches.

## Story

As the maintainer,
I want the CLI package prepared, proven and tagged for its first npm release,
So that `npx gitnebula` works for a stranger with nothing but Node installed.

## Context (binding)

- AD-11: pure ESM; `contract`, `scanner`, `deps`, `githist` are source-only
  internal packages; exactly two build edges (viz via Vite, cli via tsup);
  **only `gitnebula` (cli) is published**; its semver is **independent of**
  `schemaVersion`.
- FR-1 (zero-config `npx gitnebula`), product principle 1.
- Story 4.1 already proved the tarball's contents and a cold install into a
  temp directory with plain npm (`packages/cli/src/pack.test.ts`). This story
  does not redo that proof; it changes the package's identity and version and
  re-runs it.
- The 2 MB gzipped viewer budget (ADR-0004) and the DoD thresholds (4.4) are
  what the released version is claimed to meet — hence the dependency on 4.4.
- **The dev-checkout asset gap (AC-6).** `packages/cli/scripts/prepack.mjs` is
  what populates `packages/cli/assets/` — the built Viewer and
  `tree-sitter-python.wasm` — and npm runs it only on `pack`/`publish`. So a
  plain `pnpm build` leaves that directory empty and the built binary dies
  with `ENOENT … packages/cli/assets/tree-sitter-python.wasm` on the first
  Python file it meets. Found by story 4.4 while measuring the DoD (PR #39),
  reported rather than patched because it was not that story's file, and left
  without an owner when 4.1 merged. The shipped tarball is correct — 4.1's
  cold-install test proves it — so this is a contributor sharp edge, not a
  shipping defect.

  It is **not a one-line fix**, and the trap is worth stating before an agent
  falls into it: the workspace `build` script runs cli **before** viz
  (`package.json`), while `prepack.mjs` requires `packages/viz/dist` to
  already exist. Wiring `prepack.mjs` into cli's own `build` therefore fails
  on a clean tree. Whichever way out is taken — reordering the two build edges
  so viz precedes cli, or a separate assets step both entry points call — it
  changes the shape of AD-11's two build edges, so the choice belongs in the
  PR body with its reasoning, and `pnpm build` must stay the only build entry
  (4.1's AC-5).

## Acceptance Criteria

- AC-1: `packages/cli/package.json` is publishable and matches AD-11:
  `private` removed, `name` is `gitnebula`, `version` is `0.1.0`, and the
  npm-page metadata is present and correct (`repository`, `homepage`, `bugs`,
  `keywords`, `description`, `license`). No other package loses `private`.
- AC-2: Every in-repo reference to the old package name still resolves —
  workspace filters in `package.json` scripts, CI steps, story specs' test
  commands and `CONTRIBUTING.md`. A grep for `@gitnebula/cli` returns only
  intentional historical mentions (Dev Agent Records, retrospectives).
- AC-3: `npm publish --dry-run` output is recorded in the story docs: the
  file list, the unpacked size, and confirmation that `dist/`, `assets/`
  (viz dist + `tree-sitter-python.wasm`) and `LICENSE` are present and that
  no source or test file is.
- AC-4: The cold-start e2e (`pack.test.ts`) passes against the renamed
  package, and its assertion on the installed **binary name** is explicit —
  `gitnebula`, from `bin`, not the package directory name.
- AC-5: `README.md`'s pre-release fallback line is replaced by the real
  post-publish text, and `CONTRIBUTING.md` gains a short **Releasing**
  section: the version bump, the dry run, the publish command, the git tag
  (`v<version>`), and the rule that CLI semver and `schemaVersion` move
  independently (AD-11).
- AC-6: After `pnpm install && pnpm build` in a fresh clone — no `npm pack`,
  no `prepack` — `node packages/cli/dist/bin/gitnebula.js <a repository
  containing Python> --no-serve` completes and emits a valid `analysis.json`.
  The proof is an automated test that fails against today's build, watched
  failing before it is relied on. `pnpm build` remains the only build entry
  (4.1's AC-5) and the published tarball's contents are unchanged — 4.1's
  `pack.test.ts` still passes untouched.
- AC-7: Owner gate — the actual `npm publish` and the `v0.1.0` tag push are
  the maintainer's, performed from a clean checkout of the merged base with
  their own npm credentials. The story prepares and proves; it does **not**
  publish. **MUST be left unticked.**

### Debug Log References

- **AC-6, watched failing first.** `pnpm --filter gitnebula exec vitest run
  src/dev-checkout.test.ts` on the unmodified branch: red at
  `expect(existsSync(join(assets, "viz", "index.html")))`. Reproduced by hand
  as well, because the first assertion short-circuits the rest:
  `rm -rf packages/cli/assets && pnpm build` left the directory absent, the
  binary died with `deps: ENOENT … packages/cli/assets/tree-sitter-python.wasm`
  on a Python repository, and aborted with
  `serve: the viewer has not been built — run \`pnpm --filter @gitnebula/viz build\``
  on a repository containing no Python at all — while
  `packages/viz/dist/index.html` existed. Green after the fix.
- **The build-lock race.** `pnpm build` and `npm pack`'s prepack both rewrite
  `packages/cli/assets/` from scratch, and until now only the former was
  serialized. A dev-checkout test that asserts what the build left behind would
  be handed a spurious pass by a concurrent `npm pack` in another vitest
  worker. `test-support.ts`'s lock was factored into `withBuildLock` /
  `withBuildLockAsync` and `pack.test.ts`'s `pack()` now takes it too.
- **`npm publish --dry-run` warned** `"bin[gitnebula]" script name was cleaned`.
  Traced to the leading `./` in the `bin` value by running `npm pkg fix` against
  a copy of the manifest in a scratch directory; the diff was that one
  character pair. Removed.
- No sign of the known fixture-repo builder race (`docs/dev/epic-3/3.6-…`) in
  any run on this branch; root `pnpm test` was green first time.
