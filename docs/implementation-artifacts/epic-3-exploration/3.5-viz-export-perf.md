## Story

As a tech lead sharing evidence — and as CI guarding the wow,
I want high-res PNG export and an automated fps measurement,
So that maps travel into documents and 60 fps stays a tested number.

## Context (binding)

- PRD FR-22, FR-14; SM-2; AD-5 (`exportPNG` re-renders through the engine
  at ≥ 2× — canvas-snapshot scaling is explicitly banned), AD-6/NFR-7
  (reduced-motion audit), Stack (Playwright, dev-only), 1.4's harness bones
  (reuse the measurement methodology; this story productionizes it).

## Acceptance Criteria

- AC-1: Export button downloads a PNG at ≥ 2× canvas CSS resolution,
  produced by an engine re-render into an offscreen target with the SAME
  camera, mode, hover/isolate state and label visibility as on screen
  (automated: export with an active highlight, decode, compare a sampled
  pixel set against the visible canvas state).
- AC-2: Filename `gitnebula-<repo-name>.png` (mockup convention).
- AC-3: Playwright harness loads the synthetic 2,000-node fixture, runs the
  scripted pan+zoom sequence (1.4's methodology), and asserts ≥ 55 fps
  sustained; runnable locally via a package script with a readable report.
- AC-4: The harness runs in CI. If runner variance forces it non-blocking
  (nightly / continue-on-error), the decision and the variance numbers are
  recorded in the docs README — silence is not an option (PRD SM-2 note).
- AC-5: Reduced-motion audit (Playwright, `prefers-reduced-motion`
  emulation): no settle animation (first frame already settled), no
  hot-spot pulse, search fly-to jumps instantly (NFR-7 — covers 2.5/3.3
  behaviours; file follow-up issues for violations found in their merged
  code rather than fixing cross-territory).

### Debug Log References

- **`exportPNG` hung the 2.5 suite before it failed it.** `engine.test.ts`
  asserted `exportPNG` rejects with the 3.5 story name; once implemented, the
  call reached jsdom's unimplemented `toBlob`, whose callback never fires, so
  the test timed out at 5 s instead of failing on the assertion. The assertion
  was removed (the member is now implemented) and the engine-level export tests
  stub `HTMLCanvasElement.prototype.toBlob`.
- **`test.use({ reducedMotion: "reduce" })` did not reach the page.** The audit
  ran green with `matchMedia("(prefers-reduced-motion: reduce)").matches ===
  false` — asserting nothing, in the file whose whole job is that assertion. A
  standalone probe confirmed `page.emulateMedia` works where the fixture option
  did not. The audit now emulates explicitly **and asserts the emulation took
  effect** before testing anything. Playwright 1.62.1; root cause not chased,
  it is not this story's defect.
- **`page.goto` resolves before the Viewer exists.** The Viewer boots
  asynchronously (it fetches `analysis.json`), so evaluating against the
  harness handle straight after navigation is a race — it surfaced as an
  intermittent `Cannot read properties of undefined (reading 'settled')` in
  whichever spec won the scheduler. Fixed in one place
  (`perf/src/page-helpers.ts`).
- **Headless Chromium is not vsync-bound.** It produced a steady 8.3 ms cadence
  (~120 fps) where the headed run reads 16.7 ms / 59 fps. Neither number is
  "the" frame rate: both are ceilings, and the honest reading is the worst
  frame against the ceiling interval. Both configurations are recorded in
  PERFORMANCE.md rather than picking the flattering one.
- **A green fps number can describe an empty canvas.** `requestAnimationFrame`
  keeps firing for a renderer that has stopped drawing, which is story 1.4's
  central lesson in a new form. Renders are now counted through a wrapped
  `getContext("2d")` and asserted against measured frames.

### Completion Notes List

- **AC-1** — `exportPNG` re-renders the scene through the same `renderFrame`
  into an offscreen surface with the context transform scaled (default and
  minimum 2×, AD-5). State parity is structural: the scene is built once and
  drawn twice, so camera/mode/hover/isolate/labels cannot diverge. The export
  reuses the **last drawn frame's clock**, because the hot-spot pulse is a
  function of time and a fresh timestamp would make "matches the visible
  canvas" untestable. Verified two ways: the export issues byte-identical draw
  calls to the live frame (jsdom), and a Playwright pixel comparison against
  the live canvas of the same instant, with a negative control proving the
  comparison can fail.
- **AC-2** — `gitnebula-<repo-name>.png`, asserted through a real browser
  download event, not only in a unit test. Names that cannot be filenames
  (`owner/repo`, spaces, reserved characters) fold to `-`; a name that needs no
  folding passes through byte for byte.
- **AC-3** — `pnpm --filter @gitnebula/viz perf`. Story 1.4's methodology,
  measuring the shipped engine: scripted keyframes derived from the *measured*
  layout extent, sustained fps as the worst sliding 1-second window, 30 warm-up
  frames excluded, run-validity guards, readable report as JSON and Markdown.
  **Verdict: PASS** — 119 sustained fps headless (three runs, identical), 59
  headed on a 60 Hz display, against a 55 floor.
- **AC-4** — `.github/workflows/perf.yml`, `workflow_dispatch` and
  `continue-on-error: true`. AC-4 forbids silence, so the README records both
  reasons (this repo's CI is dispatch-only until 4.2; hosted runners rasterise
  canvas 2D in software) **and the variance numbers**: three consecutive local
  runs produced identical sustained fps and ≤ 0.1 ms spread at p95 — the
  instability that justifies non-blocking is in the environment, not the
  harness.
- **AC-5** — Reduced-motion audit, all three legs asserted: first frame already
  settled (`durationMs === 0`, camera unchanged across 20 frames), no pulse
  (byte-identical canvas over 700 ms), and fly-to instant (the camera is at its
  destination one frame after the call). A control test with animation enabled
  proves the stillness check is not vacuous. The fly-to leg was written as a
  probe that skipped with a recorded reason while story 3.3 still owed
  `flyTo`; 3.3 merged during this story and the assertion went live with no
  edit — the suite went from 7 passed / 1 skipped to **8 passed / 0 skipped**.
  No NFR-7 violation was found in merged code, so no follow-up issue was
  filed.
- **Deviation, announced, agreed, and then exercised:** `buildScene` is
  pamela's method (3.3). It was written here only because this story has
  `depends_on: []` and the export needed a scene. Her PR #24 merged into the
  epic branch mid-story and the agreed rule was applied to the real conflict:
  **her `buildScene` body, this story's `exportPNG` body**. Her version is a
  superset (member file nodes, `member: true` edges, the `pulse` field), so
  resolving by "take the epic branch's side" without reading it would have
  dropped unfold from the render path while still compiling and type checking.
  Three follow-on details from that rebase: her `buildScene` is public on the
  class rather than private (chrome still cannot reach it — `GraphEngine` does
  not declare it), `draw()` regained this story's one line recording the frame
  clock, and story 2.5's `notYet()` helper was removed because `flyTo` and
  `exportPNG` were its last two callers.
- **One new seam:** `src/harness-handle.ts` publishes `{ engine, settled }` so
  the harness can drive the real Viewer. No UI reaches it, nothing in `viz`
  reads it, and it exposes only what AD-5 already exposes to chrome.
- **Difference from 1.4 recorded rather than glossed:** per-frame *work* times
  are not reported. The shipped engine owns its loop behind the seam;
  instrumenting it would mean editing `engine.ts` to time itself, in a method
  two cohort peers are editing, for a number no AC asks for. Frame-interval p95
  and worst-frame carry the stutter signal instead. Stated in PERFORMANCE.md.
- **Numbers were re-measured after 3.3 merged**, rather than shipping the
  pre-unfold figures with a caveat. Phase `c` fell from 119 to 81–85 sustained
  fps headless with worst frames of 17.6–25.1 ms; phase `b`, which never
  crosses `UNFOLD_ZOOM`, did not move at all, which is the control that
  attributes the difference to unfold rather than to noise. On the 60 Hz
  display both phases read 59 sustained and 17.7 ms worst frame — unfold is
  free there, because its work fits in the ~8 ms of slack a 60 Hz frame
  leaves. The headroom it consumes is real and would show as an occasional
  hitch at 120 Hz; recorded in PERFORMANCE.md as a finding for a later story,
  not a failure here. Both configurations clear the 55 floor.
- **The export inherited unfold with no code change**, as designed: it
  re-renders the scene, so exported PNGs now contain unfolded member nodes,
  member edges and the search-arrival pulse. The pixel-parity test compares
  against the live canvas rather than a golden image, so it kept passing across
  the merge with no new baseline.

**Harness defects found, reported, not fixed** (per the supervised-cohort
addendum):

1. `intent-ready.sh` warns that `intent.md` lacks sections it contains. Its
   check runs `grep -qE "^## ${section//\'/\\\'}"`, escaping the apostrophe to
   `\'`, which is undefined in ERE — so every section title with an apostrophe
   ("What I'm doing", "Files I'll touch") never matches. Cosmetic, worked
   around by verifying the sections by hand.
2. `git stash` is shared across linked worktrees (reported by arnold, who lost
   time to it: his `stash pop` pulled pamela's uncommitted 3.3 files into his
   checkout). This story used one stash/pop cycle before the warning arrived,
   verified afterwards that only its own files returned, and committed to the
   branch before every subsequent rebase — of which there were four, as bob's
   #19, alice's #21, pamela's #24 and the #26/#20 pair landed on the epic
   branch during the story.
3. The workspace-level `pnpm test` still races in `githist` on the shared
   fixture repository (story 3.6's subject). Per-package runs are clean;
   `pnpm --filter @gitnebula/viz test` is this story's test command anyway.
