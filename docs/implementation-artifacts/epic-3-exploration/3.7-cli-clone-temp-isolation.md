# Story 3.7: Scope the clone temp-dir assertions to what the test owns

> **Status: ready-for-dev** · Owner: `cli` · Touches: `packages/cli/` (test
> files only) · Depends_on: `[3.2-cli-serve-url]`
>
> 3.2 is already merged (PR #19, `629a14c`), so the dependency is satisfied
> on any base that carries the epic head. Nothing else blocks this story.
>
> **You change what a test observes, never what it asserts about the
> product.** `cloneRepository` and `dispose()` are correct and are not the
> defect; do not touch `packages/cli/src/clone.ts` or any other source file.
> If you find yourself weakening the leak check rather than scoping it, stop
> — a test that no longer notices a leaked temp directory is worse than the
> flake.

## Provenance

This story was written by the **supervisor of `epic/3-deps-python`**
(terminal-agents agent `superman`) on 2026-08-13, during the epic, out of
supervision rather than planning. The maintainer agreed to it being specced
as a new story in the same session.

It exists as a new story rather than as a correction to a working agent
because **nobody owns the defect**: it is in story 3.2's merged test code,
`bob` finished and is `done`, and the only agent still touching that package
(`chuck`, 3.6-fixture-build-race) is barred by his own spec from changing
what another story's test asserts. `chuck` reported it rather than patching
it, which was the correct call and is the reason this file exists.

**Evidence.**

- `chuck` reported 3 failures in 8 runs of
  `pnpm --filter @gitnebula/cli test` on the unmodified epic head, and 7/10
  on his own rebased branch with all three failures being this one
  assertion and none in the fixture builder.
- The supervisor reproduced it independently in a detached worktree at the
  unmodified epic head `629a14c` — fresh `pnpm install`, nothing from any
  story branch — and measured it worse: **5 failures in 8 runs** (runs
  1, 2, 3, 5, 7 red; 4, 6, 8 green). Always the same test:

  ```
  FAIL  src/clone.test.ts > an unreachable URL aborts in the AD-7 shape (AC-5)
        > names the URL, suggests the remedy, and leaves no temp dir
  AssertionError: expected [] to deeply equal [ 'gitnebula-clone-hJuxVL' ]
  ```

**Mechanism.** `cloneTemps()` (`packages/cli/src/clone.test.ts:74`) lists
*every* directory in the shared system temp directory whose name starts with
`gitnebula-clone-`, including directories this test never created. The same
package's other suites create and dispose directories with that prefix in
parallel vitest workers. So the `before` snapshot (line 174) can capture a
sibling suite's live temp directory, which is gone by the time the
assertion re-lists at line 184 — and the test fails over a directory that
has nothing to do with it. Line 161 (`dispose()` leaves nothing behind) has
the identical shape and is exposed to the same race; it happens to lose the
coin toss less often.

**Why it matters beyond the noise.** `3.6-fixture-build-race` AC-1 asks for
ten consecutive clean root runs, and this flake makes that unachievable
through no fault of that story. `4.2-ci-pages-recipe` will turn CI on over
the same command.

## Context (binding)

- The product behaviour under test is right and stays: an aborted clone must
  leave no temp directory behind (3.2 AC-5), and `dispose()` must remove the
  checkout (3.2 AC-4). **Both assertions must still fail if that behaviour
  regresses** — prove it, see AC-3.
- AD-8: the suite is offline. The failing test deliberately uses
  `http://127.0.0.1:1/` so nothing touches the network; keep that.
- Test-only change. No source file under `packages/cli/src/` other than
  `clone.test.ts` (and, if you need one, a new test helper) may be modified.

## Acceptance Criteria

- AC-1: `pnpm --filter @gitnebula/cli test` passes **10 consecutive times**
  from a clean checkout on a base carrying `629a14c`. Record the ten runs in
  the story README. (The supervisor's baseline for comparison: 3 of 8 green
  before the change.)
- AC-2: Both temp-directory assertions — `clone.test.ts:161` and
  `clone.test.ts:184` at the time of writing — observe only directories the
  test itself created. A sibling suite creating or disposing a
  `gitnebula-clone-*` directory at any moment must not be able to affect
  either result. Mechanism is yours (compare against the checkout roots the
  test made; give the test its own temp root; both) — state what you chose
  and what you rejected in the story README.
- AC-3: Both assertions are proven still able to fail for the right reason:
  break the behaviour they cover (make `dispose()` a no-op; make the abort
  path skip its cleanup) and show each goes red. Record both, red and green,
  in the story README. **An assertion that cannot fail is the failure mode
  this story is most likely to introduce.**
- AC-4: No change to any file outside `packages/cli/src/clone.test.ts` and
  any new test-support file you add. `packages/cli/src/clone.ts` is
  untouched — `git diff --stat` in the PR body proves it.
- AC-5: The rest of the package is unaffected: the full
  `pnpm --filter @gitnebula/cli test` count is the same 114 tests as before,
  minus nothing, and `pnpm lint` exits 0.
