# Story 3.8: The full path of a truncated search result

> **Status: ready-for-dev** · Owner: `viz` · Touches: — · Depends_on:
> `[3.3-viz-navigation]`
>
> 3.3 is merged, so the dependency is satisfied on any base carrying the Epic 3
> head. Nothing else blocks this story.
>
> **The truncation is not the defect and must not be "fixed".**
> `.search-result-name` truncates from the front on purpose (`direction: rtl`
> with `text-overflow: ellipsis`), which keeps the basename — the part that
> says which file a result is. Removing the ellipsis, wrapping the text, or
> widening the box are all out of scope. What is missing is a way to read the
> whole path without opening the result.

## Provenance

Written by the **supervisor of `epic/3-deps-python`** (terminal-agents agent
`superman`) on 2026-08-13, at epic closure, out of supervision rather than
planning. The maintainer agreed to it being specced in the same session.

It exists as a new story because nobody owns it: 3.3 is merged, its author is
`done`, and **no acceptance criterion covers it** — 3.3's AC-3 requires the
persistent box, fuzzy matching, the top 7, keyboard navigation and the camera
flight, and says nothing about reading a result that does not fit its row.

**Evidence.** The maintainer found it during their own manual pass over the
merged Epic 3 head, searching `ass` on this repository: three of seven results
rendered as `…viewport-scoped-semantic-unfold.md`,
`…ets/tree-sitter-python.wasm.sha256` and
`…finition-and-hot-spot-threshold.md`, with no way to tell which directory any
of them lives in. The supervisor confirmed the cause in the merged code:
`packages/viz/src/chrome/search.ts:104-116` builds each option and sets
`name.textContent = node.path` and nothing else — no `title`, on neither the
`li` nor the span — while `packages/viz/src/styles.css:293-301` does the
truncating. So the full path is present in the DOM as text that is visually
clipped and unreachable by hover.

This is a UX gap of the kind only a human pass finds: every automated check in
3.3 asserts on `textContent`, which is complete and correct.

## Context (binding)

- `title` is already the established mechanism in this chrome — `export-button.ts`
  and `header.ts` both use it for their controls. Use the same one rather than
  introducing a custom hover layer.
- **Do not reuse the canvas tooltip component from 3.3** (`chrome/tooltip.ts`).
  That one follows the cursor over the map and belongs to hover-on-node; a
  second consumer would couple search chrome to it for no benefit.
- The search listbox follows the ARIA combobox pattern. A `title` must not
  disturb `aria-activedescendant`, the option ids, or the polite live region.

## Acceptance Criteria

- AC-1: Every rendered search result carries its **full path** as a `title`, so
  hovering a truncated row reveals it. A test asserts the attribute equals
  `node.path` for a result long enough to be clipped.
- AC-2: The truncation behaviour is unchanged — `direction: rtl`,
  `text-overflow: ellipsis`, the basename still visible. A test or a recorded
  manual observation shows a long path still ending in its basename, not its
  first segment.
- AC-3: Nothing else in the listbox regresses: the ARIA wiring, the top-7 cap,
  keyboard navigation and the existing 3.3 search tests all still pass
  unchanged.
- AC-4: Audit the rest of `chrome/` for the same gap — any other element that
  clips text it owns gets the same treatment, or the audit records that there
  is none. At the time of writing, `.search-result-name` is the only rule in
  `styles.css` using `text-overflow: ellipsis`.

### Completion Notes List

- `name.title = node.path` in `search.ts`'s `render()`, for the pointer.
- **A search result had no accessible name at all, and now has one.** The
  maintainer ran this story's `MANUAL_TESTING.md` step 7 — the screen-reader
  step I had left for a human — and VoiceOver announced a result as "You are
  currently on a menu item, group, inside a list box", with no path in it.
  Chrome's accessibility tree confirmed the cause against the running app:
  every `role=option` had an **empty name** and both its spans were exposed as
  separate generic nodes, while every other element on the page was named. ARIA
  says this should not happen — `option` is children-presentational — but the
  engine does not flatten it. Fixed by authoring the name:
  `option.setAttribute("aria-label", \`${node.path}, ${node.kind}\`)`. That
  also supplies the separator name-from-content would not: the spans otherwise
  run together as `assemble.tsfile`. Verified after the change in the same
  tree, with clipped rows announcing their full path —
  `option "docs/adr/0006-viewport-scoped-semantic-unfold.md, file"`.
  **This is a 3.3 defect, not a regression of this story**; it is fixed here
  because it is the same element, because this story's own reasoning had
  asserted the opposite, and because a story about reading a search result that
  a screen-reader user cannot read is not done. Blast radius is `search.ts`
  alone, so it was fixed rather than escalated, and it is flagged at the top of
  the PR body.
- **The `title` is on `span.search-result-name`, not on the `li[role=option]`.**
  The spec fixed the mechanism but not the element. The span is what clips, and
  it has no ARIA role, so the attribute cannot reach name computation. On the
  `li` it would have become the option's accessible description and been read
  out after the name. A test asserts the `li` has no `title` so the choice is
  not reversible by accident.
- Seven tests added, in their own describe block with their own `setNodes`
  fixtures so no existing 3.3 assertion's inputs move. Every one of them was
  watched fail before its fix landed.
- `styles.css` has **no diff** in this branch — the truncation is untouched, as
  the spec requires.
- **AC-4 audit: no other gap.** `text-overflow: ellipsis` appears exactly once
  in `packages/viz/src/styles.css`, on `.search-result-name`. The four other
  `white-space: nowrap` rules were each checked and none clip: `.tooltip` sizes
  to its content, `.visually-hidden` is never rendered, `.p-badge` is a
  one-word badge, `.p-row span:first-child` holds authored-short metric labels.
  The panel's path and value cells wrap (`overflow-wrap: anywhere`) instead of
  clipping. Table in the story README.
- **Deviation from the Tasks list, deliberate.** The spec expected
  `MANUAL_TESTING.md`'s steps to stay unticked for the owner. The project rule
  is that executable steps are executed, so they were, with observed results
  recorded inline — 7 of 9 now, the file having grown two steps in the course
  of the VoiceOver finding. The two unrun steps are the native tooltip's actual
  rendering (an OS-level widget painted outside the page bitmap, so it cannot
  be screenshotted headless) and the re-run of the VoiceOver announcement. Both
  need a human at a real machine and both say so in the file. The second is
  worth the minute: it is the step that caught the missing accessible name.
- No `PERFORMANCE.md`: one attribute assignment per option on a list capped at
  seven touches no stated performance property.
- Verified: `pnpm --filter @gitnebula/viz test` 369 passed (31 files),
  `typecheck` clean, `pnpm lint` clean, `pnpm build` clean.
