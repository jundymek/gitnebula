# Story 3.8: The full path of a truncated search result

> **Status: ready-for-dev** · Owner: `viz` · Touches: — · Depends_on:
> `[3.3-viz-navigation]`
>
> 3.3 is merged, so the dependency is satisfied on any base carrying the Epic 3
> head. Nothing else blocks this story.
>
> **The truncation is not the defect and must not be "fixed".**
> `.search-result-name` truncates from the front on purpose (`direction: rtl`
> with `text-overflow: ellipsis`), which keeps the basename — the part that
> says which file a result is. Removing the ellipsis, wrapping the text, or
> widening the box are all out of scope. What is missing is a way to read the
> whole path without opening the result.

## Provenance

Written by the **supervisor of `epic/3-deps-python`** (terminal-agents agent
`superman`) on 2026-08-13, at epic closure, out of supervision rather than
planning. The maintainer agreed to it being specced in the same session.

It exists as a new story because nobody owns it: 3.3 is merged, its author is
`done`, and **no acceptance criterion covers it** — 3.3's AC-3 requires the
persistent box, fuzzy matching, the top 7, keyboard navigation and the camera
flight, and says nothing about reading a result that does not fit its row.

**Evidence.** The maintainer found it during their own manual pass over the
merged Epic 3 head, searching `ass` on this repository: three of seven results
rendered as `…viewport-scoped-semantic-unfold.md`,
`…ets/tree-sitter-python.wasm.sha256` and
`…finition-and-hot-spot-threshold.md`, with no way to tell which directory any
of them lives in. The supervisor confirmed the cause in the merged code:
`packages/viz/src/chrome/search.ts:104-116` builds each option and sets
`name.textContent = node.path` and nothing else — no `title`, on neither the
`li` nor the span — while `packages/viz/src/styles.css:293-301` does the
truncating. So the full path is present in the DOM as text that is visually
clipped and unreachable by hover.

This is a UX gap of the kind only a human pass finds: every automated check in
3.3 asserts on `textContent`, which is complete and correct.

## Context (binding)

- `title` is already the established mechanism in this chrome — `export-button.ts`
  and `header.ts` both use it for their controls. Use the same one rather than
  introducing a custom hover layer.
- **Do not reuse the canvas tooltip component from 3.3** (`chrome/tooltip.ts`).
  That one follows the cursor over the map and belongs to hover-on-node; a
  second consumer would couple search chrome to it for no benefit.
- The search listbox follows the ARIA combobox pattern. A `title` must not
  disturb `aria-activedescendant`, the option ids, or the polite live region.

## Acceptance Criteria

- AC-1: Every rendered search result carries its **full path** as a `title`, so
  hovering a truncated row reveals it. A test asserts the attribute equals
  `node.path` for a result long enough to be clipped.
- AC-2: The truncation behaviour is unchanged — `direction: rtl`,
  `text-overflow: ellipsis`, the basename still visible. A test or a recorded
  manual observation shows a long path still ending in its basename, not its
  first segment.
- AC-3: Nothing else in the listbox regresses: the ARIA wiring, the top-7 cap,
  keyboard navigation and the existing 3.3 search tests all still pass
  unchanged.
- AC-4: Audit the rest of `chrome/` for the same gap — any other element that
  clips text it owns gets the same treatment, or the audit records that there
  is none. At the time of writing, `.search-result-name` is the only rule in
  `styles.css` using `text-overflow: ellipsis`.
