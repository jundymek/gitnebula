### The five claims of E6-17, with where each is currently true

Pointers, not permission to transcribe. Every one must be re-verified against
the tree you are standing in, and the PR body cites `path:line` for each.

1. **`boot()` previously had no test execution.** Its only caller is
   `packages/viz/src/main.ts`; `packages/viz/src/app-view-swap.test.ts:23` says
   in its own words that "`boot()` itself is not exercised here — it fetches
   `analysis.json`". It is executed now, by `packages/viz/ui/tests/boot.pw.ts`.
   The claim is about what was true **before** this epic; write it as history,
   with what replaced it.
2. **Production capture/restore is authoritative for view-state carryover.**
   `captureState`/`restoreState` are closures inside `boot()` in
   `packages/viz/src/app.ts`; `ui/tests/view-swap.pw.ts` drives the real ones
   across a 2D→3D→2D round trip, over all eight `CarriedState` fields.
3. **Whether the former test-only carry helper remains necessary.** The helper
   is `carry()` at `packages/viz/src/app-view-swap.test.ts:50`, whose own
   comment says it is "Kept in step with `captureState`/`restoreState` in
   `app.ts`". Story 6.2 answered the question — **keep it** — and gave the
   reason: it runs in jsdom on every `pnpm test` with no browser installed,
   while the browser specs run only on demand; what changed is that the
   duplication is no longer load-bearing, because drift now shows up in
   `view-swap.pw.ts`. Record the answer and the reason. If your own reading of
   the tree contradicts it, say so rather than repeating it.
4. **Why real-coordinate picking is not representable by the jsdom fake
   canvas.** `packages/viz/src/test-support/fake-canvas.ts:113-123` replaces
   `HTMLElement.prototype.getBoundingClientRect` globally with a fixed box at
   the viewport origin, and `devicePixelRatio` is 1 in jsdom, so every
   client-to-canvas conversion subtracts zero. In the real page the canvas sits
   below the header. `ui/tests/pointer-hit.pw.ts` is what covers it now.
5. **The requirement to reacquire the harness handle after swaps.**
   `publishHarnessHandle(engine)` is called inside `swapEngine`
   (`packages/viz/src/app.ts:267`), so a handle cached across a view change
   refers to a destroyed engine. `ui/tests/view-swap.pw.ts` demonstrates the
   trap rather than merely avoiding it.

### E6-06 — the separation

`packages/viz/package.json` declares three scripts: `test` (`vitest run`),
`ui` (`playwright test -c ui/playwright.config.ts`) and `perf`. The `ui` suite
is **not** reachable from `pnpm test`, deliberately: `pnpm test` must keep
passing on a machine with no browser installed (contract criterion E6-05). Say
what runs the suite, that it is on demand, and why the separation exists.
