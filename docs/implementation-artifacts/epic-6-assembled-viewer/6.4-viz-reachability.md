## Story

As a reader on a short screen looking at a file with many co-change partners,
I want the panel's actions to stay reachable,
So that content past the fold scrolls into view instead of being lost.

## Context (binding)

- `epics.md` Epic 6; FR-27 (blast radius), FR-26 (start-here), UX-DR14 (empty
  and bounded states name their cause).
- **Why this story exists.** The guard that exists today is a **regex over the
  stylesheet**. `packages/viz/src/chrome/blast-radius.test.ts:412-431` reads
  `styles.css` as text and asserts that `max-height:` and `overflow-y: auto`
  appear in the `.p-blast-list` and `#panel` rules. Its own comment calls this
  "a weaker check than a rendered one, and still enough to catch the cap being
  deleted". It would pass with `max-height: 0`, it would pass if a later rule
  overrode the cap, and it would pass if a flex parent broke it.
- **The defect it guards is real and was measured.** `styles.css:874-881`
  records it: `body` is `overflow: hidden`, so anything past the fold is
  **unreachable rather than merely off-screen**; one real file on this
  repository has **44 co-change partners**, and at ~23 px a row that is over
  1,000 px of list, which pushed the `show on map` toggle and the panel's own
  actions below the viewport where they could not be reached at all.
- **Three regions depend on real viewport height**, and jsdom computes no
  layout for any of them:
  - `#panel` — `max-height: calc(100% - 36px); overflow-y: auto`
    (`styles.css:389-390`)
  - `#start-here` — the same bound (`styles.css:529-530`)
  - `.p-blast-list` — `max-height: min(38vh, 320px)` (`styles.css:884-885`)
- **No source reads `scrollTop`, `scrollHeight` or `scrollIntoView`** anywhere
  in `packages/viz/src/`. So there is no scroll *behaviour* to test — the thing
  to verify is **reachability**: that a control is inside the viewport and
  clickable. Do not invent scroll-position assertions; assert that the reader
  can get to the control.
- **The tooltip's flip has never run against a measured box.**
  `packages/viz/src/chrome/tooltip.ts:104-107` measures `element.offsetWidth`
  and `offsetHeight`, and in jsdom both are always **0**. The pure function
  `tooltipPosition` is already tested exhaustively, including a grid sweep of
  the viewport asserting the never-overflow invariant
  (`chrome/tooltip.test.ts:46-86`) — **do not re-test the function.** What is
  untested is the chain "real font renders → real text width → correct flip",
  because its inputs have never been real. Note that
  `tooltip.test.ts:116-122` passes only because the box is 0×0.
- **The tooltip carries `aria-hidden="true"`** (`tooltip.ts:89`), so it is
  invisible to role and accessible-name queries by construction. Select it by
  class or by its element, and assert its **rendered rectangle**.
- **This closes an item Epic 5 left open.** `docs/dev/epic-5/5.6-viz-blast-radius/MANUAL_TESTING.md:96`
  carries "Scrolling felt in a browser" unticked, because the agent had no
  browser and no eyes. The mechanism is automatable; whether it *feels* right
  is not, and the two must not be conflated.
- **Fixture.** `root-files` is small but has only one co-change pair, so it
  cannot produce a long list. To exercise the 44-partner case you need a
  document with a long partner list — build one for your specs from a valid
  base, and do **not** add it to `packages/contract/fixtures/`. State in the
  README how you produced it, so the measurement is reproducible.
- **Determinism (AD-6).** Await `settled` before measuring anything
  positional — never a timeout.

## Acceptance Criteria

- AC-1: With the panel open on the node carrying the longest co-change list,
  at a viewport of 1280×800 **and** again at a height of about 600 px, the
  `show on map` control and the panel's own actions are inside the viewport
  and clickable. The check is a **rendered** one — element boxes measured in
  the browser — not a match against stylesheet text.
- AC-2: Each of the three bounded regions — `#panel`, `#start-here`,
  `.p-blast-list` — scrolls its own content when filled past its cap, and none
  of them pushes a control outside the window.
- AC-3: The reachability assertion is shown able to fail, using the negative
  control pattern story 6.1 established: with the height cap defeated, the test
  goes red. A check that cannot fail is not a check.
- AC-4: A node with a long path is hovered near the right edge and near the
  bottom edge, and the tooltip's **rendered rectangle** stays inside the
  viewport — the flip proven against a measured box rather than a 0×0 one.
- AC-5: `packages/viz/src/chrome/tooltip.ts` and `tooltip.test.ts` are
  unchanged: this story tests the function's real inputs, not its logic, which
  is already covered.
- AC-6: The story's README records, for each region, the measurement that
  makes the case concrete — the list length used, the viewport heights, and
  whether any control was found unreachable. If one is, it is **reported, not
  fixed**: changing shipped layout needs its own story.
- AC-7: No file under `packages/viz/src/` is modified, no fixture is added to
  `packages/contract/fixtures/`, no dependency is added, and every new spec is
  a **new file** under `packages/viz/ui/tests/`.
- AC-8 (human-review): The "scrolling felt in a browser" item that story 5.6
  left unticked is revisited — either ticked with the evidence named, or
  restated in `MANUAL_TESTING.md` as the part that remains genuinely
  subjective now that the mechanism is covered.
