## Story

As the maintainer,
I want a browser suite that can be run on demand and is proven able to fail,
So that the stories after me add coverage instead of each inventing a harness.

## Context (binding)

- `epics.md` Epic 6; AD-5 (the `GraphEngine` / chrome split), AD-8 (offline by
  construction). No FR — this epic verifies, it does not add product.
- **Why this story exists, and what it must not become.** An earlier framing of
  this epic said "nothing drives the chrome through a real browser". That is
  false and you must not restate it. Two Playwright suites already exist and
  carry **14 tests**: `packages/viz/perf/tests/` (fps, fps-3d, degradation-3d,
  export, reduced-motion) and `packages/viz/bundle/tests/bundle.pw.ts`. Roughly
  **318 jsdom tests across 21 files** in `packages/viz/src/chrome/` already
  assert the readouts, driving components with fake engines. **Your suite is a
  skeleton plus a proof that it can fail — it adds no behavioural coverage.**
  Coverage is wave B's job.
- **The port convention is not yours to choose.** `PERF_PORT` defaults to
  4318 (`packages/viz/perf/playwright.config.ts:23`), `BUNDLE_PORT` to 4319
  (`packages/viz/bundle/playwright.config.ts:27`). You take **4320** and
  **`UI_PORT`**, continuing the series.
- **`reuseExistingServer: false` and `--strictPort` are load-bearing.** The
  comment in `perf/playwright.config.ts:69-70` records the incident: with
  several agent worktrees on one machine, a green run was traced by `lsof` to
  another checkout entirely. Do not relax either setting, and do not let the
  suite fall back to a running server.
- **`openViewer` exists and must not be rewritten.** It lives at
  `packages/viz/perf/src/page-helpers.ts` and its docstring explains why it is
  needed: `page.goto` resolves on the load event, but the viewer boots
  asynchronously — it fetches `analysis.json` before it can build an engine —
  so the harness handle appears *after* navigation resolves. Promote it to a
  location both suites import; do not fork it, and do not change its behaviour.
- **Import `HARNESS_HANDLE_KEY`**, never the literal `"__gitnebula"`. It is
  exported from `packages/viz/src/harness-handle.ts:17`.
- **The suite runs outside `pnpm test`.** This was decided at planning time
  with the maintainer and is not yours to revisit: `perf` and `bundle-check`
  are both explicit scripts, and `pnpm test` must not start requiring a
  browser. Wire `ui` the same way.
- **Fixtures.** `GITNEBULA_FIXTURE` selects the document
  (`packages/viz/vite.config.ts`); a bare name resolves against
  `packages/contract/fixtures/<name>.json`. A missing fixture 404s loudly on
  purpose — story 1.4 learned that a silent fallback produces a run that looks
  normal while measuring nothing. Do **not** add a fixture: `root-files`
  (6 nodes, 3 layers, 3 cross-layer file edges, one co-change pair) is the
  default for interaction work and is what wave B will use.
- **House style, from the existing suites:** `testDir: "./tests"`,
  `testMatch: "**/*.pw.ts"`, `workers: 1`, `fullyParallel: false`,
  `retries: 0` ("a perf run is evidence, not a flake to retry away"), a fixed
  `viewport` and `deviceScaleFactor: 1`, and a prose failure message as the
  second argument of every `expect`.

## Acceptance Criteria

- AC-1: `packages/viz/ui/` carries a Playwright config with `testDir: "./tests"`,
  `testMatch: "**/*.pw.ts"`, `workers: 1`, `fullyParallel: false`,
  `retries: 0`, a fixed `viewport` and `deviceScaleFactor: 1`, matching the
  two existing configs; asserted by reading the config in a test or by the
  suite running under it.
- AC-2: The suite's dev server starts with `reuseExistingServer: false` and
  `--strictPort` on port **4320**, overridable by `UI_PORT`; running two
  suites concurrently on one machine cannot silently share a server. The
  config carries a comment naming the `lsof` incident so the setting is not
  "tidied up" later.
- AC-3: `pnpm --filter @gitnebula/viz ui` runs the suite. `pnpm test` is
  **unchanged** — it does not invoke Playwright and does not require a browser;
  asserted by the fact that `pnpm test` passes in an environment with no
  browser installed, and stated in the story's README.
- AC-4: `openViewer` is promoted out of `packages/viz/perf/src/` to a location
  both suites import, its behaviour byte-unchanged; the `perf` suite is updated
  to the new path and `pnpm --filter @gitnebula/viz perf` still passes. No spec
  in either suite calls `page.goto` directly.
- AC-5: The suite carries at least one **negative control** in the shape
  `packages/viz/perf/tests/export.pw.ts:165` uses ("the parity check can fail:
  a stale export stops matching a changed screen") — a test that demonstrates
  the positive assertion would go red against a deliberately wrong
  expectation. A suite that cannot be shown to fail is not evidence.
- AC-6: `HARNESS_HANDLE_KEY` is imported rather than `"__gitnebula"` written
  out, and every `expect` in the suite carries a prose failure message as its
  second argument; asserted by a check over the suite's own sources, in the
  shape `5.6`'s no-`localeCompare` check used.
- AC-7: No dependency is added beyond what `perf` and `bundle` already use, no
  file under `packages/viz/src/` is modified, and no fixture is added
  (`CLAUDE.md`: nothing no story asks for).

### Debug Log References

**1. The `--strictPort` check was itself false-green, and watching it red is
what found it.** The first version of the AC-2 assertion in
`ui/src/suite-conventions.test.ts` was `config.includes("--strictPort")`.
Deleting the flag from `webServer.command` left the test passing, because the
explanatory comment beneath the setting mentions the flag too — the check was
satisfied by prose. It now extracts the `command:` template literal and asserts
against that; re-running the same mutation with the comment intact fails
correctly. This is the same class of defect the story's own AC-2 is about: a
harness that keeps reporting, just not on the thing under test.

**2. `fps-3d.pw.ts` went red on the first full `perf` run, and it is not this
story's doing.** The `c-unfold-pan` phase asserts a 20 fps usability floor. It
measured below it while a second agent was building on the same machine; re-run
alone it measured 21 fps and passed, and a subsequent full-suite run was 10
passed. Story 5.7 already recorded this phase at **22 fps**
(`docs/dev/epic-5/5.7-viz-3d-view/PERFORMANCE.md:47`), so the assertion sits
~1–2 fps above its own floor and flips under load. The entire `perf` diff in
this story is five import lines, none of which the 3D renderer loads. Reported,
not retuned — the measurement belongs to whoever owns it.

**3. A `.gitignore` gap in Playwright's default `outputDir`.** A red run wrote
traces to `packages/viz/ui/test-results`, which `.gitignore` does not cover
(it covers `packages/viz/test-results/`). Fixed inside this suite's own config
via `outputDir: "../test-results/ui"` rather than by editing shared ignore
rules. `perf` and `bundle` have the same latent gap; left alone.

**4. A harness gate misfired repeatedly, and the cause was the working
directory.** After intent-sync completed, `Edit`/`Write` calls were blocked with
"cohort intent-sync incomplete". `hooks/pre-tool-use.sh:2829` tests
`"$CWD/intent.synced"`, where `CWD` is the tool call's working directory — so
any call issued from a subdirectory after a `cd packages/viz` cannot see the
marker. Superman independently diagnosed the same cause and is reporting it to
the maintainer. Worked around by issuing every command from the worktree root
and letting `pnpm --filter` do the scoping, which is the form the stack brief
asks for anyway. Nothing about it was patched here: it is a terminal-agents
defect, not a gitnebula one.
