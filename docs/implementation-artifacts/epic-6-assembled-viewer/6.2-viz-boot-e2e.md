## Story

As a reader switching between the 2D and 3D views,
I want the view change to keep what I was looking at,
So that the map is a different view of my frame rather than a reset.

## Context (binding)

- `epics.md` Epic 6; FR-32 (3D view as a co-equal alternative), AD-5 (the
  `GraphEngine` / chrome split), AD-6 (seeded layout and the Settled
  definition).
- **Why this story exists — the epic's strongest fact.** `boot()`
  (`packages/viz/src/app.ts`) is executed by **no test in the repository**.
  Its only caller is `packages/viz/src/main.ts:9`. That is roughly 120 lines
  that fetch the document, render the error screen on failure, mount the
  chrome, parse `?view=3d`, build the engine and wire the search box and
  tooltip. `packages/viz/src/app-view-swap.test.ts:23` says so in its own
  words: "`boot()` itself is not exercised here — it fetches `analysis.json`".
- **The real `swapEngine()` is never called either**, and this is the sharp
  end. `app-view-swap.test.ts:50-69` defines a local `carry()` helper that
  reimplements the capture/restore logic, and its own comment says it must be
  "kept in step with" `app.ts`. **Deleting a field from `restoreState` in
  `app.ts` would fail no test.** Your job is to make the real function the
  thing under test.
- **The four ordering constraints inside `swapEngine`
  (`app.ts:244-280`), each of which documents a defect it exists to prevent:**
  1. `viewSwitch.setCurrent(built.view)` — the switch reflects what was
     **built**, not what was asked for, so a 3D request that fell back does
     not leave "3D" looking selected.
  2. `setUnavailable(unavailabilityAfterSwap(...))` — probing unconditionally
     after a swap re-enabled the button and erased the constructor's reason in
     exactly the case AC-5 of story 5.7 exists for: `?view=3d`, probe passes,
     constructor throws, fall back to 2D, and the reader is shown an enabled
     3D button and no explanation.
  3. `publishHarnessHandle(engine)` **before** `engine.load(analysis)` —
     under reduced motion the settle is announced synchronously inside
     `load()`, so the harness has to be listening by then (AD-6).
  4. `restoreState` **after** `load()` (which resets interaction state by
     design) and **before** `connectEngine`, so the chrome reads the restored
     state on connect rather than the defaults followed by a flurry of change
     events.
- **The handle is republished on every swap.** `publishHarnessHandle` is
  called inside `swapEngine`, so a test that caches
  `globalThis[HARNESS_HANDLE_KEY]` across a view toggle holds a **destroyed**
  engine. Re-read the handle after every swap, and make the suite demonstrate
  this rather than merely avoiding it.
- **What is already covered, and what you must therefore not write.**
  `app-view-swap.test.ts` has 15 tests: state carry-over field by field in both
  directions, the null/default case, the blast radius, the return-to-scope
  ordering, `swapWithFallback`, `unavailabilityAfterSwap` and
  `failedSwitchReason`. The 3D engine **is** constructed for real in jsdom —
  it is a perspective projection onto a 2D canvas (`engine3d.ts:212` is
  `getContext("2d")`), **there is no WebGL anywhere**, so there is no
  WebGL-absent path to test. Reduced-motion boot ordering is covered twice
  over, in `chrome/start-here-wiring.test.ts:113-150` and in
  `packages/viz/perf/tests/reduced-motion.pw.ts`. **Do not re-assert any of
  it.** Your contribution is that the real `boot()` and the real
  `swapEngine()` run.
- **The hit-testing blind spot.** `packages/viz/src/test-support/fake-canvas.ts:113-123`
  monkeypatches `HTMLElement.prototype.getBoundingClientRect` globally to a
  fixed 1200×800 at origin (0,0), and `devicePixelRatio` is always 1 in jsdom.
  The engine reads that rect in five places to convert client coordinates to
  canvas coordinates. So the excellent `pick()` grid scan in
  `engine.test.ts:290-305` runs against a canvas that is always at the viewport
  origin — in the real page the canvas sits below the header. A rect-offset
  bug would be invisible to every existing test.
- **Fixture:** `root-files` — 6 nodes, three layers (`backend` 2, `infra` 2,
  `test` 1), 3 cross-layer file edges, one co-change pair. Small, real, and
  every node reachable. Select it with `GITNEBULA_FIXTURE`; a missing fixture
  404s loudly on purpose.
- **Determinism (AD-6, NFR-12).** The same `analysis.json` always settles into
  the same map, seeded by `hash(repo.name)`. Await `settled` before asserting
  anything positional — never a timeout.

## Acceptance Criteria

- AC-1: A test opens the viewer in a browser and exercises the **real**
  `boot()` — not a reconstruction — asserting through the harness handle that
  an engine was built and that `settled` resolved. The story's README states
  plainly that before this story `boot()` had zero executions in the test
  suite.
- AC-2: `?view=3d` boots directly into the 3D view, asserted through the
  handle. This is unreachable in jsdom because `boot()` fetches
  `analysis.json`, and it is the URL the perf harness and a human both use to
  reproduce a 3D run.
- AC-3: With a mode, a layer filter, a scope, connected-only and a selection
  set by a reader, clicking the view switch and then switching back carries
  every one of them, asserted through the handle after each swap — and the
  assertions run against the real `captureState`/`restoreState` in `app.ts`,
  not against a reimplementation. The README states which of the two is now
  authoritative for that behaviour, and whether
  `app-view-swap.test.ts`'s `carry()` helper is still needed.
- AC-4: The suite demonstrates the republish trap: a cached handle held across
  a view change refers to a destroyed engine, and the correct pattern is
  re-reading `globalThis[HARNESS_HANDLE_KEY]` after the swap. Demonstrated by a
  test, not only documented in prose.
- AC-5: After a successful 3D swap the view switch's pressed state reflects the
  view that was **built**; and when the 3D constructor throws, the reader is
  left on a working 2D map showing the constructor's own reason rather than a
  probe's verdict. Both assertions go through the real `swapEngine` path.
- AC-6: A node is clicked at real screen coordinates in the browser, with the
  canvas positioned below the header, and the node the reader aimed at is the
  one that becomes selected — asserted through `getSelected()`. The story's
  README names why this is unreachable in jsdom, quoting the fixed rect in
  `fake-canvas.ts:113-123`.
- AC-7: The suite adds no product code — `packages/viz/src/` is unmodified —
  adds no dependency, adds no fixture, and every new spec is a **new file**
  under `packages/viz/ui/tests/`. `pnpm --filter @gitnebula/viz perf` and
  `pnpm --filter @gitnebula/viz test` both still pass.
- AC-8 (human-review): Watching the suite run, the view switch behaves the way
  the tests claim on a real repository's map. Recorded as an unticked item in
  `MANUAL_TESTING.md`.
