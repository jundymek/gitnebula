**Evidence.** arnold (story 5.8) reported it at 18:57 in peer message
`from-arnold-001`, having reproduced it on a clean clone of
`epic/5-onboarding` at `4ffbee0`. bob (story 5.7) confirmed it independently

```
$ git show origin/epic/5-onboarding:packages/viz/src/engine/layout.ts \
    | sed -n '230,245p' | cat -v | grep -n '\^@'
9:    const key = `${source}^@${target}`;

$ for f in $(git ls-tree -r --name-only origin/epic/5-onboarding -- packages/viz/src); do
    n=$(git show origin/epic/5-onboarding:$f | tr -dc '\0' | wc -c)
    [ "$n" != "0" ] && echo "$f: $n NUL"
  done
packages/viz/src/engine/layout.ts: 1 NUL
```

`^@` in `cat -v` is a literal 0x00 in the file. The byte entered the
repository in `ad3d099` (`feat(viz): draw the repository's root files`,
PR #45, 2026-08-14): the same file at `ad3d099^` carries zero NUL bytes and at
`ad3d099` carries one. It has survived every review since, which is the point
of the story rather than an aside — `git diff`, GitHub's diff view, an editor
and a code review all render it as nothing at all.

**The blast radius of the defect, measured.** arnold measured the emitted
`analysis.json` from a clean clone at `4ffbee0` and corrected his own earlier
report to me, to alice and to bob (peer message `from-arnold-002`, 19:15):

```
packages/viz/src/engine/layout.ts
  out-edges: 3  -> engine/graph.ts, engine/prng.ts, engine/settle.ts
  in-edges:  4  <- engine/camera.ts, engine/engine.ts, engine/layout.test.ts, engine/navigation.test.ts
  loc: 0
```

So the file **keeps its import edges** and loses only its line count: `deps`
does not read the scanner's `binary` flag. The node is drawn at minimum size
with its coupling intact. This is the cosmetic-but-visible defect, not the
worse one — the map does not understate the engine's coupling. AC-5 still
asks the story for its own before/after run rather than inheriting this
number, but the implementer starts from a measured expectation instead of a
guess. Reproduce with:

```
node -e 'const d=JSON.parse(require("fs").readFileSync("analysis.json","utf8"));const id="packages/viz/src/engine/layout.ts";console.log(d.edges.filter(e=>e.source===id).length, d.edges.filter(e=>e.target===id).length)'
```

**Why this is a defect and not a curiosity.** `packages/scanner/src/walk.ts:24`
defines `NUL = 0x00` and line 242 returns `{ loc: 0, binary: true }` for any
file containing it; `packages/scanner/src/analyze.ts:65` then records a
`binary-file` warning. So gitnebula's map **of its own repository** shows its
own force-layout engine as an empty binary node. The tool is a portfolio piece
whose demo maps this repository (story 5.8, AC-3), so the defect is on the
path to the thing a visitor sees first.

**Third occurrence, and the reason it needs a check rather than a fix.** The
same idiom was fixed once already, in a fixture, by the story 5.1 agent during
wave A. bob had copied it into `layout3d.ts` before arnold's message reached
him and corrected his own file. arnold's own `DECISIONS.md` picked up a raw
NUL while he was quoting the offending line — caught by his codex auto-review,
gitignored, never committed. Three occurrences in one epic, from three agents
who could all read the line, is the strongest available evidence that a human
or an LLM re-reading the source is not a control that works here.

**Why a new story and not a correction to a live agent.** `engine/` is inside
both 5.6's and 5.7's territory for their own features, but the separator is in
neither story's acceptance criteria, and the repo-wide check belongs to no
story in the cohort. Correcting a live agent would have made one of them
responsible for a defect predating their branch. Nobody owns it, so it is a
story.

## Story

As a visitor looking at gitnebula's map of gitnebula,
I want every source file in the repository to be read as source,
So that the tool does not present its own layout engine as an empty binary
node.

## Context (binding)

- The scanner is **correct** and is not the subject of this story. Treating a
  NUL-bearing file as binary is deliberate, tested
  (`packages/scanner/src/analyze.test.ts:386`) and is what any sane file
  walker does. The fix belongs in the file that contains the byte.
- The separator's *purpose* is legitimate: a composite map key needs a
  separator that cannot occur in either half. NUL was chosen for exactly that
  property. The replacement must preserve it — a separator that can appear in
  a node id reintroduces key collisions, which is a worse defect than the one
  being fixed.
- **Determinism (NFR-4, AD-4) is unaffected but must stay unaffected**: the
  key is internal to layout, and changing its spelling must not change any
  value that reaches `analysis.json`.
- `packages/viz` is the only package involved. The package-boundary rules
  (`viz` → `contract` only) and the ESLint clock/RNG ban are untouched by this
  work.
- Everything in the repository is in English (`CLAUDE.md` language protocol).

## Acceptance Criteria

- AC-1: No tracked **text or source** file contains a literal NUL byte. The
  separator in `packages/viz/src/engine/layout.ts` is replaced by one that
  is still guaranteed not to occur in a node id, and the reason for the
  choice is stated in a comment at the site. Genuine binary assets are
  excluded and must not be touched — `docs/assets/demo.gif`, the PNGs under
  `docs/dev/epic-4/4.4-dod-validation/` and
  `packages/deps/assets/tree-sitter-python.wasm` legitimately contain NUL
  bytes. The story states the rule it uses to tell the two apart, and that
  rule must be **independent of file content** — a source-extension
  allow-list or an explicit `.gitattributes` declaration, never git's own
  binary detection. Git classifies by content: a file is binary to git
  *because* it contains a NUL, so a content-based rule would exclude from the
  check precisely the file the check exists to catch. That circularity is the
  defect in miniature, and AC-2's check inherits the same requirement.
- AC-2: An automated check fails when a tracked text source file carries a
  NUL byte, and it is wired into a command that already runs — the root
  `pnpm test` tooling check added by story 5.9 is the obvious host, and
  reusing it is preferred to adding a second entry point. The check names the
  offending file and byte offset, because the byte is invisible in every
  other tool a reviewer looks through.
- AC-3: The check was watched fail before being relied on: re-introduce a NUL
  into a source file, observe the named failure, restore, observe green.
  Recorded in `MANUAL_TESTING.md` with the observed output.
- AC-4: The scanner's binary detection is **not** modified, and
  `packages/scanner/src/analyze.test.ts`'s binary-file expectations still
  pass unchanged. A fix that makes the scanner tolerate NUL fails this AC.
- AC-5: The observed effect is recorded before and after, from a real run of
  the pipeline over this repository: the node for
  `packages/viz/src/engine/layout.ts` and whether it carries a `binary-file`
  warning, its `loc`, and its import edges in both directions. The expected
  answer is in the provenance section above — 3 out, 4 in, `loc: 0`, measured
  by arnold before this story was scheduled — and this AC is satisfied by
  reproducing it on the branch and showing the after state, not by citing it.
- AC-6: `pnpm lint`, `pnpm test` and `pnpm build` are green, and the viz
  suite's summary line is quoted in the PR body.

### Completion Notes List

- **AC-1, first deviation: the key is removed, not re-spelled.** No sound
  replacement byte exists — the halves are node ids, i.e. paths, and a POSIX
  path may contain any byte but NUL and `/`. `seen` is now
  `Map<string, Set<string>>`, so the halves never share a string and no
  separator is needed. Behaviour-identical: same dedupe, same insertion order,
  same output. The reason is a comment at the site, as AC-1 requires.
- This is the shape `topLevelLinks3D` in `layout3d.ts` already uses, merged and
  tested, written by `bob` for story 5.7 for the same reason and offered to me
  as prior art in `from-bob-001`. He also flagged that `add()` must keep
  dropping self-links **ahead of** the map lookup, which it does.
- **AC-1, second deviation: the classification rule is a binary-extension
  deny-list**, not the source allow-list or `.gitattributes` the AC names. It
  meets the AC's actual requirement — content-independent, never git's own
  detection — and it fails **closed**: a new text extension is checked by
  default, where an allow-list would skip it in silence. That silent skip is
  the same defect shape this story exists to close. `.gitattributes` was
  rejected because parsing its pattern language is more code than a
  sixteen-element set and a partial parser is a new place to be quietly wrong.
- **AC-2** is hosted in `scripts/verify-test-commands.mjs`, the story 5.9
  entry point already inside root `pnpm test`, as the spec prefers. The finding
  names file, line and byte offset.
- **Codex found a real hole in the first version of the check and it was
  fixed, not dismissed.** The sweep decoded `git ls-files -z` as UTF-8, so a
  tracked file whose *name* is not valid UTF-8 decoded to a different string,
  the read failed, and the `catch` skipped it silently — the story's own defect
  wearing a different hat. Paths now stay raw `Buffer`s to `readFileSync`, the
  extension test decodes `latin1` (byte-preserving), and an unreadable tracked
  file is **reported rather than skipped**. The end-to-end case cannot be
  staged on APFS, which refuses non-UTF-8 filenames with `EILSEQ`; it is
  reachable on the ext4 of `ci.yml`'s runner, so the fix is kept and verified
  at the level this machine allows (byte round-trip and the unreadable branch),
  which `MANUAL_TESTING.md` §6 records honestly rather than overclaiming.
- **AC-4 verified two ways**: `git status --short packages/scanner/` is empty,
  and the scanner suite passes 150/150 including the binary-file expectation at
  `analyze.test.ts:386`.
- No other tracked text file carried a NUL, so the sweep in the task list found
  nothing further to fix.
- `sprint-status.yaml` is untouched on the supervisor's instruction
  (`from-superman-003`): he sets this row by hand at closure, because the
  script cannot derive it from a branch named for 5.9.
- Contract untouched, `schemaVersion` unchanged, no new dependency, no
  package-boundary change.
