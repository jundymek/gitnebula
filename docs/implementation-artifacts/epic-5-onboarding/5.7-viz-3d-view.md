## Story

As a developer exploring a dense repository,
I want a three-dimensional view of the same graph,
So that a cloud that overlaps in the plane can be separated by depth.

## Context (binding)

- PRD FR-32; NFR-3 (≥ 55 fps automated floor at 100 modules / 2,000 files),
  NFR-13 (3D either holds that floor or documents its own measured floor and
  the node count at which it degrades), NFR-7 and UX-DR15 (reduced motion),
  NFR-11 (no contract change), AD-5 (the `GraphEngine` seam), AD-6
  (determinism), ADR-0004 (static bundle, ≤ 2 MB gzipped viewer).
- **The seam is the point.** AD-5 declared the `GraphEngine` interface as a
  swap seam and FR-14 called for exactly this. 3D is a *second implementation
  behind that interface*, not a fork of the renderer.
  `chrome/boundary.test.ts` must keep passing **unchanged** — if it needs
  editing, the seam is being violated; stop and report rather than relaxing
  the test.
- **A working prototype exists**:
  `/private/tmp/claude-501/-Users-jundymek-dev-gitnebula/d538167c-5c7e-4871-a716-931164ab6b2f/scratchpad/nebula3d/`
  — a standalone, dependency-free page: perspective projection onto the same
  2D canvas the shipping viewer uses, force simulation across three axes,
  seeded PRNG (`hashString` + `mulberry32`, the same pair as the shipping
  engine), depth fog as a density cue, the mockup palette and
  `HOT_THRESHOLD = 0.5`. It demonstrates that 3D is achievable **without
  Three.js and without WebGL**, which is what keeps ADR-0004's bundle budget
  and the no-WebGL fallback tractable. It is a throwaway experiment: read it
  as prior art and as an existence proof, not as a base to apply.
- **Determinism (AD-6).** The 3D layout and the initial camera orientation
  are seeded from the document, exactly as the 2D layout is. No unseeded
  randomness anywhere in the view; the repository's `Date.now`/`Math.random`
  lint bans (AR-9) apply here too.
- **Zero contract change.** The 3D view reads the same `analysis.json`;
  `schemaVersion` stays `"1.0"` (NFR-11).

## Acceptance Criteria

- AC-1: The 3D view is a second implementation behind the `GraphEngine`
  interface, switchable at runtime, with **2D remaining the default**; chrome
  reaches it through the same interface and events, and
  `chrome/boundary.test.ts` passes unchanged (AD-5, FR-32).
- AC-2: Loading the same `analysis.json` twice produces an identical 3D
  layout and identical initial camera orientation, seeded from the document;
  asserted by a test that builds two engines and compares positions. No
  unseeded randomness appears anywhere in the view (AD-6).
- AC-3: The automated perf harness runs against the 2,000-node fixture in 3D
  and **either** holds the ≥ 55 fps floor **or** records a measured floor and
  the node count at which it degrades, in
  `docs/dev/epic-5/5.7-viz-3d-view/README.md`. An unmeasured 3D view does not
  satisfy this story (NFR-3, NFR-13).
- AC-4: The viewer bundle still passes ADR-0004's 2 MB gzipped budget with
  the 3D view included, asserted by the existing bundle-size check.
- AC-5: On a machine without working WebGL, the absence of 3D degrades to the
  2D map with a stated reason rather than a blank canvas — asserted by a test
  that simulates the unavailable path (product principle 1: always a useful
  result).
- AC-6: Under `prefers-reduced-motion`, entering the 3D view produces no
  auto-rotation and no entry animation (UX-DR15, NFR-7).
- AC-7: A new ADR under `docs/adr/` records the decision and its consequences
  for AD-5, AD-6 and ADR-0004, in the repository's context → decision →
  consequences format. Numbered as the next free ADR (`0007`) unless another
  story has taken it — check before writing.
- AC-8 (human-review): On a real dense repository, depth separates clusters
  that overlap in the plane, and the 3D view is worth switching to. Recorded
  as an unticked item in `MANUAL_TESTING.md`.

### Debug Log References

- **`boundary.test.ts` decided the layout's implementation.** Its final
  assertion pins `d3-force` importers to exactly `["layout.ts"]`. Since the
  spec requires that test to pass unchanged, `layout3d.ts` is hand-rolled and
  imports no simulation library. The constraint and the prototype's design
  agreed, so nothing had to be escalated.
- **Two mutation checks, one of which found a weak test.** After the projection
  and layout suites went green, key assertions were re-run against deliberately
  broken implementations. The near-plane guard and the depth tie-break were both
  caught. "Spreads the cloud across all three axes" was **not** — collapsing
  `node.z += node.vz` in the integrator still passed, because the seeded scatter
  already supplies depth. A second test was added asserting that z *changes*
  during the settle, which the same mutation does fail.
- **`SettleDetector` is structurally 2D.** It measures `hypot(dx, dy)`, so a
  cloud frozen in the plane while still expanding in depth would report Settled.
  `SettleDetector3D` imports the same `SETTLE_DISPLACEMENT_PX` / `SETTLE_FRAMES`
  constants, so AD-6 keeps one definition.
- **AC-2's orientation half was initially unobservable.** The manual walkthrough
  compared `getOrientation()` across two loads and saw yaw differ by 0.0016 rad.
  That was idle auto-rotation advancing the live camera between load and read —
  one frame of drift, not a seeding defect. `getInitialOrientation()` was added
  so the pose AC-2 is actually about can be compared, with a test that pins it
  while the live orientation moves.
- **Code review found two real regressions in the view swap**, both fixed, both
  covered by tests confirmed to fail against the previous behaviour:
  - `connectEngine`'s teardown called `search.destroy()`, removing a
    document-level shortcut listener. Correct for a page teardown, wrong for a
    swap — the search box is created once and reused by every engine, so after
    one 2D→3D switch it looked present and answered nothing. `ConnectOptions`
    gained `destroyControls`, defaulting to `true` so no existing caller
    changes; the swap passes `false`.
  - A swap rebuilt the engine with defaults, silently discarding view mode,
    layer filter, scope, connected-only, selection and isolate. That is the same
    defect this story argued against when 5.6 offered to let the blast radius
    vanish on the switch. `app.ts` now captures that state **through the
    interface** and restores it after `load()` — filters before interaction
    state, so the engine's own reconciliation does not undo it.
  - Both re-verified in a real browser: search returns the same 7 results after
    two swaps, and mode/layers/scope/selection survive 2D→3D.
  - A second review round found two more, both fixed and both covered by
    mutation-verified tests. **The carried state omitted the co-change mark**,
    so the capability this story insisted on drawing in 3D would have vanished
    on the switch anyway — the same defect it had argued against, one layer up.
    **A fallback reason could be erased by the probe that ran after it**: on
    `?view=3d` with a passing probe and a throwing constructor, the swap fell
    back with a stated reason and an unconditional probe then returned `null`,
    re-enabling the button and deleting AC-5's explanation. The decision is now
    the pure function `unavailabilityAfterSwap`, where a real failure's reason
    always beats a probe.
- **`hiddenCount().visible` ignores the layer filter** when no scope and no
  connected-only filter is active — it short-circuits to `graph.nodes.length`,
  contradicting the interface's own doc comment. Found because the degradation
  sweep read 2,100 for every sample. The measurement was moved to the scene the
  renderer is actually handed. Pre-existing, identical in the 2D engine,
  belongs to 5.3/5.4: reported, not fixed.
- **NUL byte in `engine/layout.ts`** (line 238, byte 8879), found by 5.8's agent
  mid-story and confirmed here at the byte level. It would have propagated:
  `layout.ts`'s joined-key idiom was already drafted into `layout3d.ts`, and a
  file read renders the NUL as an ordinary space, so it copies invisibly.
  `layout3d.ts` dedups through a nested map with no separator at all. The
  original report said the file also loses its imports; its author measured and
  corrected that — only `loc` is lost, the edges survive (3 out, 4 in) — and
  this record reflects the corrected version. Now story 5.10; not fixed here.
  Method note worth keeping: `grep -rlP '\x00'` finds nothing on this
  repository even where the NUL is; count bytes (`od`/python) instead.

### Completion Notes List

- **All eight ACs are met.** AC-8 is the human-review item and is left unticked
  in `MANUAL_TESTING.md`, as the spec asks.
- **The seam held.** `chrome/boundary.test.ts` has a **zero-line diff** and
  passes. No 2D engine module (`engine.ts`, `layout.ts`, `render.ts`,
  `camera.ts`) is touched, and no case was added to any existing 2D test file —
  every 3D test is in a new file, agreed with 5.6's owner so two parallel
  stories never meet in a merge.
- **AC-5 diverges from the spec's wording, deliberately.** The criterion says
  "on a machine without working WebGL", but this 3D view does not use WebGL —
  it projects onto canvas 2D, which the spec's own Context section praises the
  prototype for proving. A literal WebGL probe would test a dependency the
  implementation does not have. Implemented as a general **view-availability
  probe**: if 3D cannot be built for any reason, the viewer degrades to the 2D
  map with a stated reason rather than a blank canvas, asserted by tests that
  simulate the unavailable path. Not escalated because the spec's own context
  contradicts the criterion's premise and the intent is unambiguous either way.
  Recorded as D4 in `DECISIONS.md` and flagged in the PR body.
- **AC-3 takes NFR-13's second option, with numbers.** 3D holds **118 fps**
  sustained on the folded map and **28 fps** unfolded at 2,100 nodes; a
  fixed-camera sweep puts the crossing **between 840 and 1,260 drawn nodes**.
  2D on the same run: 119 / 92 fps. All in `PERFORMANCE.md` with the commands
  that reproduce them. The 3D perf spec asserts run *validity* and a 20 fps
  usability floor rather than the 55 fps floor, because NFR-13 accepts a
  documented lower floor and asserting it would turn an accepted characteristic
  into a red build.
- **AC-4 measured against a real baseline.** 65,716 B → 70,814 B gzipped
  (**+5,098 B, +7.8 %**), 3.37 % of ADR-0004's 2 MB budget. The before-figure
  came from building `epic/5-onboarding` out of a clean `git archive`
  extraction, not from memory.
- **The orbit camera is derived from `CameraState`, not added to it** (D2).
  `k` → orbit distance, `x`/`y` → orbit target, yaw/pitch → engine-internal
  interaction state. Widening `CameraState` would have been a breaking change
  forcing every 2D consumer to carry two meaningless fields — weakening the
  seam this story exists to prove.
- **3D simulates top-level nodes only, with local member wakes** (D3), exactly
  as 2D does. The prototype put every file in one cloud; copying that would
  have made 3D a *different map* rather than the same map from another angle,
  and `unfoldedModules()` is on the interface.
- **`setBlastRadius`/`getBlastRadius` were implemented ahead of 5.6's interface
  change**, by agreement with its owner, so neither PR could block the other in
  either merge order. The mark is **drawn**, not merely stored: 5.6 explicitly
  offered the discount and it was declined, because a blast radius that vanished
  on the view switch would falsify this story's central claim. 5.6 has since
  merged; this branch is rebased onto it, `Nebula3DEngine` satisfies the widened
  interface with no edit, and the ring now **imports** `COCHANGE_RING_*` from
  `constants.ts` instead of the locally transcribed copies it carried while that
  PR was open.
- **Two shared files touched beyond the plan**, both additive and both explained
  above: `test-support/fake-canvas.ts` gains a `measureText` recorder (the 3D
  label grid needs metrics; the 2D renderer never measured text), and
  `chrome/chrome.ts` gains the `destroyControls` option from the code review.
- **`styles.css` deliberately untouched** — 5.6's territory this wave. The
  switch carries the shared `modes` class and uses `aria-pressed`, this
  repository's established segmented-control pattern, so the pressed state is
  already styled by `.modes button[aria-pressed="true"]` with no new CSS.
- **A renderer optimisation was measured, costed and not taken** — see
  `PERFORMANCE.md` §3. The per-node radial gradient dominates and most nodes
  project to a few pixels, so flat discs or a sprite atlas would likely move the
  knee past 2,100. No AC asks for it and it would change the shared node
  encoding (UX-DR4).
